## Why this matters

Everything in this module so far, from regular expressions to the combined DFA to longest match, can be done for you by a tool. You write the patterns and what to do for each one, and the tool writes the lexer. **Lex** is the original tool of this kind, from Unix. **Flex** is the free reimplementation most people use today, and it reads the same format with some additions. In this lesson, "Lex" means the format and "Flex" means the program you run.

Flex reads your specification and generates a C file named `lex.yy.c`, which contains a function called `yylex`. You compile that file like any other C code:

```text
flex wc.l            # generates lex.yy.c from your specification
gcc lex.yy.c -o wc   # compiles the scanner
./wc < input.txt     # runs it
```

The visualizer in this lesson runs the same matching rules, but it uses a simplified rule format, **not real flex syntax**. It has a name and a pattern on each line and no C code. The Worked example section shows the two formats side by side.

## The file structure

A Lex file has three sections, separated by lines containing only `%%`:

```text
declarations
%%
rules
%%
user code
```

- **Declarations.** C code between `%{` and `%}`, which is copied unchanged to the top of `lex.yy.c`. Also name definitions such as `digit [0-9]`, and start condition declarations, which come later in this lesson.
- **Rules.** One per line: a pattern, some whitespace, and an action written in C. The pattern must start at the very beginning of the line.
- **User code.** C code copied unchanged to the end of `lex.yy.c`, usually helper functions and often `main`.

The Dragon Book calls the last two sections translation rules and auxiliary functions.

## A complete program

This word counter, in a file named `wc.l`, is a complete Flex program:

```lex
%{
#include <stdio.h>
int lines = 0, words = 0, chars = 0;
%}

WORD    [^ \t\n]+

%%

{WORD}  { words++; chars += yyleng; }
\n      { lines++; chars++; }
.       { chars++; }

%%

int yywrap(void) {
    return 1;
}

int main(void) {
    yylex();
    printf("%d lines, %d words, %d characters\n", lines, words, chars);
    return 0;
}
```

The first section declares three counters and defines the name `WORD` as any run of characters other than space, tab and newline. The rules section says what to do for a word, a newline and any other single character. The last section supplies `yywrap` and `main`.

None of the actions here contains a `return`, and that matters. When an action finishes without returning, `yylex` just carries on scanning, so this single call to `yylex` runs all the way through the input.

## How Lex patterns differ from ordinary regular expressions

Lex patterns look like the regular expressions you may know from Python or JavaScript, and most of the operators are the same: `|`, `*`, `+`, `?`, parentheses and `.`, which matches anything except a newline. The differences are what catch people out:

| In Lex | Meaning | Watch out for |
| --- | --- | --- |
| `"a+b"` | The literal text `a+b`. Inside quotes, operators lose their meaning. | In most other regex dialects, a quote is an ordinary character. |
| `[a-z]`, `[^0-9]` | A character class, or its negation. | Inside a class, most operators are literal. Only `\`, `-`, `]` and a leading `^` stay special. |
| `{digit}+` | One or more of whatever the name `digit` was defined to be. | Without braces, `digit+` means the letters `digi` followed by one or more `t`s. |
| `a{2,3}` | Two or three `a`s. | Braces around a number mean a repeat count, and around a name mean a definition. |
| A space | Ends the pattern, unless it is quoted, escaped or in a class. | Write `"a b"`, because `a b` means the pattern `a` and then something else. |
| `\d` | The letter `d`. | Flex has no `\d` or `\w`. Write `[0-9]`. |
| `r/s` | `r`, but only when `s` follows. `s` is not consumed. | Called trailing context. A `/` to match must be quoted or escaped. |
| `^r`, `r$` | `r` at the start or the end of a line. | |

Two more differences come from how Lex works. It builds a DFA, so there are no backreferences, no capture groups and no lazy operators. And `|` does not prefer its left side, as it does in Python or JavaScript. There, `if|iffy` on `iffy` matches `if`, but Lex always takes the longest match.

## The names you will use

| Name | What it is |
| --- | --- |
| `yylex()` | The scanning function Flex generates. Each call reads input until an action executes `return`, and returns that value. At the end of the input it returns 0. |
| `yytext` | The text of the current lexeme, as a null-terminated string. |
| `yyleng` | The length of `yytext`. |
| `yylval` | A global variable an action uses to pass the token's attribute value to the parser. Yacc declares it for you. |
| `yywrap()` | Called when the input runs out. Returning 1 means there is no more input, so `yylex` returns 0. Returning 0 means you have pointed `yyin` at another file, so scanning continues. |

`yytext` changes on the next match. If you need to keep a lexeme, copy it, for example with `strdup`.

You need to deal with `yywrap` in one of three ways: define it yourself, as the word counter does, put `%option noyywrap` in the declarations to say you do not want it, or link Flex's own library with `-lfl`, which supplies one. Otherwise, linking fails with an undefined reference to `yywrap`.

## Which rule wins

Lex settles ambiguity exactly as the last lesson described:

1. Always prefer the longest possible match.
2. If several patterns match that longest text, prefer the one listed first.

```lex
"if"      { return IF; }
[a-z]+    { return ID; }
```

On `if`, both rules match two characters, so the first wins. On `iffy`, the second matches four characters, so it wins. If you swap these two lines, `if` becomes an `ID`, and Flex warns that the `"if"` rule cannot be matched. The visualizer gives a similar warning.

<TryIt visualizer="token-stream" source="if iffy" rules="ID  [a-z]+  %identifier
IF  if      %keyword
WS  [ \t\n]+ %skip">Try the rules in the wrong order</TryIt>

What if no rule matches at all? Flex has a default rule that copies the unmatched character to the output and moves on, so stray characters get printed, not reported. If you want to report them, end your rules with a catch-all such as `.`, whose action reports an error.

## Start conditions

Sometimes the same characters need different rules depending on context. Inside a block comment, `if` is not a keyword, and a newline only needs counting. Start conditions let you switch sets of rules:

```lex
%x comment
%%
"/*"            { BEGIN(comment); }
<comment>"*/"   { BEGIN(INITIAL); }
<comment>\n     { lines++; }
<comment>.      { /* skip it */ }
```

`%x comment` declares a start condition. A rule prefixed with `<comment>` is active only in that condition. `BEGIN(comment)` switches into it, and `BEGIN(INITIAL)` returns to the default condition, which every scanner starts in. Inside the comment, longest match still applies, so `*/` beats the single character that `.` would take. If the input ends inside the comment, these rules report nothing and `yylex` simply returns 0, but Flex has a special end-of-file pattern you can use to catch that.

The two kinds of declaration differ in what happens to rules with no prefix:

| Declared with | Rules marked with this condition | Rules with no prefix |
| --- | --- | --- |
| `%s name` (inclusive) | Active | Active |
| `%x name` (exclusive) | Active | Not active |

For comments you want `%x`. With `%s`, a rule like `[a-z]+` would stay active inside the comment, and it would beat `.` by longest match on every word.

The alternative is a single pattern for the whole comment, which is possible but hard to get right. It is `"/*"([^*]|\*+[^*/])*\*+"/"`, and the visualizer can run it, because that pattern is valid in its format too.

<TryIt visualizer="token-stream" source="x /* a * b */ y" rules='COMMENT "/*"([^*]|\*+[^*/])*\*+"/"  %comment
ID      [a-z]+                       %identifier
WS      [ \t\n]+                     %skip'>Match a comment with one pattern</TryIt>

<Callout kind="textbook">
The book describes Lex, while start conditions, `%option` and `BEGIN(name)` with parentheses are given here as Flex has them. Original AT&T Lex has only inclusive start conditions, and it writes `BEGIN name;` without parentheses, a form Flex also accepts. Flex makes `yytext` a pointer by default, while some Lex versions use an array. Check these details against the manual for the tool you are using.
</Callout>

## Connecting to Yacc

A scanner rarely runs alone. Usually it serves a parser generated by **Yacc**, or its free reimplementation **Bison**. The parser function `yyparse` calls `yylex` each time it needs a token:

| Step | What happens |
| --- | --- |
| 1 | The Yacc file declares tokens with `%token NUMBER`. Running `yacc -d` writes their codes into a header, `y.tab.h`. |
| 2 | The Lex file includes that header, so its actions can `return NUMBER;`. |
| 3 | `yyparse` calls `yylex`, which scans until an action returns a token code. |
| 4 | Before returning, the action stores any attribute value in `yylval`, where the parser reads it. |
| 5 | At the end of the input, `yylex` returns 0, which tells the parser the input is finished. |

```lex
%{
#include <stdlib.h>
#include "y.tab.h"
%}
%%
[0-9]+     { yylval = atoi(yytext); return NUMBER; }
"+"        { return PLUS; }
[ \t\n]+   { /* skip whitespace */ }
```

The first rule shows the whole arrangement: the token code is the return value, and the value of the number travels separately in `yylval`. The whitespace rule has no `return`, so `yylex` simply continues to the next lexeme. Building both takes three commands, assuming `parser.y` supplies `main` and `yyerror`, and that the scanner defines `yywrap` or uses `%option noyywrap`:

```text
yacc -d parser.y                 generates y.tab.c and y.tab.h
flex scanner.l                   generates lex.yy.c
gcc y.tab.c lex.yy.c -o calc     compiles both together
```

## Worked example

Run the word counter on this input, which has a newline after `cat` and another after `sat`:

```text
the cat
sat
```

The scanner works through it like this:

| Lexeme | Rule that wins | Why | `lines` | `words` | `chars` |
| --- | --- | --- | --- | --- | --- |
| `the` | `{WORD}` | Three characters against one for `.` | 0 | 1 | 3 |
| space | `.` | `{WORD}` cannot match a space | 0 | 1 | 4 |
| `cat` | `{WORD}` | Longest match | 0 | 2 | 7 |
| newline | `\n` | `.` does not match a newline | 1 | 2 | 8 |
| `sat` | `{WORD}` | Longest match | 1 | 3 | 11 |
| newline | `\n` | Only this rule matches | 2 | 3 | 12 |

At the end of the input, `yywrap` returns 1, `yylex` returns 0, and `main` prints:

```text
2 lines, 3 words, 12 characters
```

Now compare a one-letter word such as `a`. `{WORD}` and `.` both match one character, so it is a tie, and `{WORD}` wins because it is listed first. Swap those two rules and one-letter words stop being counted, while longer words still are.

The visualizer has the same three rules loaded. Press play to confirm the order of lexemes above, and then try the tie:

NL     \n         %punctuation
OTHER  .          %operator">Scan one-letter words</TryIt>

Here is how a Flex rule set translates to the visualizer's format:

```lex
"if"                    { return IF; }
[a-zA-Z_][a-zA-Z0-9_]*  { return ID; }
[0-9]+                  { return NUM; }
[ \t\n]+                { /* skip */ }
```

```text
IF   if                      %keyword
ID   [a-zA-Z_][a-zA-Z0-9_]*  %identifier
NUM  [0-9]+                  %literal
WS   [ \t\n]+                %skip
```

In the visualizer's format, there are no C actions, only a token name and tags. `%skip` stands in for an action that returns nothing, and the other tags only choose colors. It has no definitions in braces, no repeat counts, no start conditions and no `yytext`. And `\d` means a digit there, while in Flex it means the letter `d`.

## Common mistakes

- **Leaving out the braces on a definition.** `digit+` matches `digi` followed by `t`s. You want `{digit}+`.
- **Putting a space in a pattern.** An unquoted space ends the pattern, and the rest of the line is taken as the action. Write `"a b"`.
- **Indenting a pattern.** Flex treats an indented line in the rules section as C code to copy, not as a rule. Patterns start in the first column.
- **Using `\d`.** It matches the letter `d`. Write `[0-9]`.
- **Keeping the `yytext` pointer.** Its contents change on the next match, so `name = yytext;` gives you garbage later. Copy the text.
- **Forgetting `return` when serving a parser.** Without it, the token never reaches the parser, because `yylex` just continues to the next lexeme.
- **Forgetting `yywrap`.** Without a definition, `%option noyywrap` or Flex's library, linking fails.
- **Assuming unmatched input is reported.** The default rule prints it to the output and carries on. Add a catch-all rule if you want an error.
- **Using `%s` where you need `%x`.** Inclusive conditions leave rules with no prefix active, so your keyword rules can still fire inside a comment.
- **Treating the visualizer's format as flex syntax.** A file in that format will not compile with flex.
